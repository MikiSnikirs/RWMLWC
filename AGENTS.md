# Правила работы агентов

В проекте работают два агента: **A** (со стороны Miki_Snikirs) и **B** (со стороны друга).
Этот файл обязателен к прочтению в начале каждой сессии.

## Порядок сессии

1. `git pull`.
2. Прочитать верх журнала второго агента (`log/A.md` или `log/B.md`).
3. Выбрать задачу в `TASKS.md`: своя зона, статус `todo`, все зависимости `done`.
4. Занять её: поставить статус `in-progress` и свою букву, **сразу закоммитить и запушить** это изменение. Так второй агент не возьмёт ту же задачу.
5. Работать в ветке `a/T-xxx-кратко` или `b/T-xxx-кратко`.
6. Прогнать тесты, привязанные к задаче (`docs/TESTS.md`), записать прогон в **свой** журнал (раздел «Прогоны»).
7. Добавить запись в **свой** журнал (шаблон — в `AGENT_LOG.md`).
8. Обновить статус задачи, открыть PR в `main`.

## Журналы: каждый пишет только в свой файл

| Файл | Пишет | Что там |
|---|---|---|
| `log/A.md` | только A | записи A, просьбы к B, ответы на просьбы B, прогоны тестов A |
| `log/B.md` | только B | записи B, просьбы к A, ответы на просьбы A, прогоны тестов B |
| `AGENT_LOG.md` | никто | архив до 14.11.2026 10:00, не дополняется |

- Просьба ко второму агенту пишется в **свой** файл с пометкой `ПРОСЬБА → A` / `ПРОСЬБА → B`. Ответ второй агент пишет в **свой** файл со ссылкой на дату просьбы.
- КОНТРАКТ и «ок» на него — так же: предложение в своём файле, «ок» во файле второго агента.
- Так двум агентам нечего править одновременно, конфликтов слияния в журналах нет.
- В `docs/TESTS.md` таблицу статусов тестов правит агент, к чьей задаче привязан тест. Таблица «Журнал прогонов» там — архив.
- PR, которые не мешают работе второго агента (не трогают его зону и `Source/Shared`), автор сливает сам.

## Зоны ответственности

| Зона | Каталоги | Агент |
|---|---|---|
| Симуляция, детерминизм, перехват ввода, карты | `Source/Client/Sim`, `Source/Client/Input`, `Source/Client/Maps` | A |
| Сервер, протокол, транспорт, хранение сейвов | `Source/Server`, `Source/Shared`, `Source/Client/Net` | B |
| Мир, торговля, режимы отсутствия | `Source/Client/World`, `Source/Client/Absence` | B |
| Интерфейс мода | `Source/Client/UI` | тот, чья задача |
| Документы, `TASKS.md` | корень, `docs/` | оба |
| Свой журнал | `log/A.md` / `log/B.md` | только владелец |

Чужую зону не правим. Если нужно изменение в чужой зоне, создаём задачу второму агенту и пишем об этом в журнал.

## Общий контракт

`Source/Shared` (сообщения протокола, форматы снимков) используют оба агента.
Любое изменение там:

- повышает `ProtocolVersion`;
- описывается в журнале с пометкой `КОНТРАКТ`;
- не сливается, пока второй агент не ответил в журнале `ок`.

## Статусы задач

`todo` → `in-progress` → `review` → `done`. Дополнительно: `blocked` (в примечании указать, чем).

Задача считается `done`, только если выполнен критерий приёмки и привязанные тесты прошли. Если тесты не запускались или упали, статус остаётся `review` или `in-progress`, а в журнале прямо написано, что не проверено.

## Честность отчётов

- Не писать «работает», если не запускалось в игре. Писать, что именно проверено и как.
- Упавший тест фиксируется в `docs/TESTS.md` с причиной, а не удаляется.
- Предположения о коде игры помечать как предположения, пока они не подтверждены декомпиляцией (`docs/research/`).

## Техника

- Цель сборки клиента: `net10.0`, Harmony 3 (строгая проверка типов `__instance`, `__result`).
- Ссылки на DLL игры берутся из локальной установки через переменную `RIMWORLD_DIR`. В репозиторий DLL игры не попадают.
- Вся логика симуляции — только детерминированная: без `DateTime.Now`, без обхода `Dictionary`/`HashSet` там, где порядок влияет на результат, без `UnityEngine.Random` и `System.Random` вне синхронизированного `Rand`.
