# Исследование симуляции RimWorld 1.7 (T-003)

Источник: декомпиляция `Assembly-CSharp.dll` и `Waylith.dll` игры 1.7.5005 rev1082 через `ilspycmd` 11.2.
Код игры в репозиторий не копируется; здесь только имена и выводы.

Как повторить у себя (папка вне репозитория):

```powershell
dotnet tool install -g ilspycmd
$env:DOTNET_ROLL_FORWARD = 'Major'
$game = $env:RIMWORLD_DIR
ilspycmd -p -o "$env:USERPROFILE\rw-decompiled\Assembly-CSharp" "$game\Assembly-CSharp.dll"
ilspycmd -p -o "$env:USERPROFILE\rw-decompiled\Waylith" "$game\Waylith.dll"
```

Пометки: **[код]** — прочитано в декомпилированном коде; **[поиск]** — только подсчёт совпадений по тексту, сами места не читались; **[вывод]** — моё заключение, не проверенное запуском.

## 1. Тик-цикл

**[код]** `Verse.TickManager.TickManagerUpdate` вызывается каждый кадр. Он копит реальное время и в цикле вызывает `DoSingleTick`, пока не отработает накопленное. Ограничения: не больше `TickRateMultiplier × 2` тиков за кадр и не дольше примерно 45 мс. На паузе выходит сразу.

**[вывод]** Число тиков за кадр зависит от частоты кадров и скорости машины. Для lockstep `TickManagerUpdate` надо заменить своим: тикать можно только до номера тика, разрешённого сервером. Это точка входа для T-014.

**[код]** Порядок внутри `DoSingleTick`:

1. `MapPreTick` для каждой карты (доступность предметов, перенос, крыши, ветер, температура, **поиск пути**).
2. Счётчик `ticksGame` увеличивается на 1.
3. Три списка тиков: обычный, редкий, долгий.
4. Мир и глобальные системы: уведомления о дате, сценарий, `World.WorldTick`, наблюдатель истории, конец игры, **рассказчик**, сказания, **квесты**, `World.WorldPostTick`.
5. `MapPostTick` для каждой карты (животные, растения, электросети, погода, лорды, игровые условия и др.).
6. История, игровые компоненты, письма, автосохранение, грязь, транспортные корабли.

## 2. Списки тиков — глобальные, не по картам

**[код]** `TickManager` держит три `TickList` на всю игру. Вещи всех карт лежат в них вперемешку. Корзина выбирается как `TicksGame % интервал`. При удалении карты её вещи вычищаются из списков отбором по `thing.Map`.

**[вывод]** Это главное следствие для архитектуры:

- «Владелец считает только свою карту» и стазис не получаются простым пропуском `MapPreTick`/`MapPostTick`: вещи карты тикают из общих списков. Нужен отбор по карте внутри `TickList.Tick` либо собственные списки на каждую карту.
- Локальные часы карты (стазис) меняют выбор корзины, потому что он привязан к глобальному `TicksGame`. Значит, для стазиса почти наверняка нужны раздельные списки по картам.
- Рассказчик, квесты и мир тикают один раз глобально. При раздельных авторитетах нужен один владелец глобального тика (сервер назначает), остальные получают результат событиями.

## 3. Генератор случайных чисел

**[код]** `Verse.Rand` — одно статическое состояние на всю игру: `seed` и счётчик `iterations`, значение считается хешем от пары. Есть стек `PushState`/`PopState`. Начальный `seed` берётся из системного времени при запуске. Пометок «на поток» нет.

**[поиск]** `UnityEngine.Random` и `System.Random` в коде игры не используются (0 файлов).

**[вывод]**

- Состояние `Rand` надо синхронизировать при входе в сессию и включать в хеш состояния (T-010).
- Один генератор на все карты и интерфейс. Чтобы карты были независимы, при тике каждой карты нужно подставлять её собственное состояние `Rand` и возвращать прежнее после.
- Любой вызов `Rand` из интерфейса сдвигает общий счётчик. Нужна изоляция (T-024): интерфейсный код работает в `PushState`/`PopState`.

### Хеш-коды как источник случайности

**[поиск]** Есть места, где генератор инициализируется хеш-кодом объекта. Большинство берут числа, координаты и клетки мира — это детерминировано. Требуют проверки те, где берётся хеш объекта-ссылки без собственного `GetHashCode`: тогда значение разное на разных машинах.

| Место | Статус |
|---|---|
| `WaterBodyTracker` (хеш водоёма) | Кандидат, не проверено, есть ли у типа свой `GetHashCode` |
| `PowerNetGrid` (хеш электросети) | Похоже на отладочную отрисовку, не проверено |
| `SubEffecter_Sprayer`, `CurvedScalerExt`, графика | Визуальное |

**[код]** У `Thing` хеш-код равен номеру вещи, то есть детерминирован (кроме вещей без номера).

### Порядок обхода `Dictionary` и `HashSet`

**[поиск]** Обход словарей встречается в 113 файлах основных пространств имён, множества используются в 236. Разобрать каждое место чтением нереально.

**[вывод]** В .NET 10 порядок обхода `Dictionary` и `HashSet` определяется порядком добавлений и удалений, а не значениями хешей. Значит, два клиента с одинаковой историей операций обходят коллекции одинаково. Расхождение возникает, когда истории разные: один клиент дошёл до состояния игрой, а другой **загрузил его из снимка** — при загрузке коллекции заполняются в другом порядке.

Следствие для архитектуры: после любой передачи снимка **обе стороны должны загрузить карту из одного и того же снимка**, включая того, кто его снял. Это касается входа в сессию (T-045), передачи авторитета (T-032), переключения на поселение друга (T-033) и авторесинка (T-034). Остаточные расхождения ловит хеш состояния и лечит авторесинк.

Этот вывод основан на знании устройства коллекций .NET, а не на проверке в игре. Его подтвердит или опровергнет T-015.

## 7. Что это меняет в плане

1. T-014: точка входа — замена `TickManagerUpdate`.
2. T-010: в хеш входит состояние `Rand`.
3. Новая задача T-005: раздельные списки тиков и состояние `Rand` по картам. От неё зависят T-032 (передача авторитета) и T-043 (стазис).
4. Новая задача T-006: аудит оставшихся потоков и источников времени (разделы 5 и 6).
5. Решить, кто владеет глобальным тиком (мир, рассказчик, квесты), когда карты считают разные клиенты. Это вопрос к T-013/T-035, зона B.
6. После передачи снимка карту перезагружают обе стороны (раздел 6а). Добавлено в критерии T-030.
7. В сценарии T-015 добавить посадку гравикорабля и смену яркости Anomaly.
